\begin{abstract}
This document specifies a production-grade architecture for \textbf{On The Porch}, a Dorchester-localized community chatbot intended to serve up to \textbf{130,000 residents}. The design optimizes for stability, data freshness, high-quality grounded answers, and \textbf{sub-5-second} response latency (p95), while supporting chat, an events panel, guest and registered authentication, and an admin dashboard. The architecture is specified from first principles, independent of any existing implementation.
\end{abstract}

\section{Product Goals and Constraints}

\subsection{What We Are Building}
A web application where Dorchester residents can ask natural-language questions about:
\begin{itemize}[noitemsep]
  \item Neighborhood news (DotNews, local RSS, community notes)
  \item City services (311 requests, response patterns, categories)
  \item Public safety (911 / crime summaries --- responsibly framed)
  \item Events (calendar, meetings, festivals)
  \item Policy and civic context (plans, anti-displacement, budgets where available)
  \item General Dorchester orientation
\end{itemize}

\subsection{Key Design Insight}
Most community chatbot implementations are slow because each question triggers \textbf{3--6 sequential LLM calls} (route $\rightarrow$ retrieve gate $\rightarrow$ SQL generation $\rightarrow$ summarize $\rightarrow$ merge $\rightarrow$ fallback). A greenfield design must \textbf{cap LLM round-trips at 1--2} and push everything else to \textbf{precomputed data, rules, and caches}.

\section{High-Level Architecture}

\subsection{Component Overview}
The system comprises six logical planes:

\begin{enumerate}[noitemsep]
  \item \textbf{Clients} --- Web SPA (mobile-responsive)
  \item \textbf{Edge} --- CDN for static assets; WAF and edge rate limiting
  \item \textbf{API layer} --- Stateless horizontally scaled services behind a load balancer
  \item \textbf{Hot-path cache} --- Redis cluster (sessions, rate limits, semantic cache)
  \item \textbf{Data plane} --- PostgreSQL (OLTP), time-series tables, vector database, object storage
  \item \textbf{Ingestion} --- Async workers scheduled via cron/queue; never on the chat critical path
\end{enumerate}

\subsection{Data Flow (Simplified)}
\begin{verbatim}
Browser (SPA)
    -> CDN (static) + WAF -> Load Balancer
        -> Auth Service
        -> Chat Orchestrator -> Redis / PostgreSQL / Vector DB / LLM APIs
        -> Events API       -> PostgreSQL (materialized events)
        -> Admin API        -> PostgreSQL (RBAC)

Scheduler -> Ingestion Workers -> PostgreSQL / Object Storage / Vector DB
\end{verbatim}

\subsection{Architectural Principles}
\begin{enumerate}[noitemsep]
  \item \textbf{Separate read path from write path} --- chat never blocks on ingestion.
  \item \textbf{Precompute before query time} --- aggregates, event lists, and embeddings are ready before a user asks.
  \item \textbf{One orchestrator, many specialists} --- single chat service coordinates SQL, vector search, and LLM; no microservice chatter on the hot path.
  \item \textbf{Fail soft, degrade gracefully} --- stale cache with disclaimer beats a 30s hang or HTTP 500.
  \item \textbf{Grounding is mandatory} --- every factual answer cites rows or document IDs used.
\end{enumerate}

\subsection{Chat Orchestrator}
The chat orchestrator is the only service on the critical path for answer quality and latency.

\subsubsection{Query Pipeline (Target: $\leq$ 5s p95)}
\begin{verbatim}
User question
  -> Tier 0: rules / exact cache / FAQ        [< 100 ms, no LLM]
  -> Tier 1: intent classification            [< 200 ms]
  -> Tier 2: parallel SQL + retrieval         [< 800 ms]
  -> Tier 3: single LLM synthesis (streamed)  [< 2500 ms]
  -> Post-process: citations + safety         [< 200 ms]
\end{verbatim}

\subsubsection{Tier 0 --- No LLM ($<$ 100ms)}
\begin{itemize}[noitemsep]
  \item Chitchat, help, identity questions
  \item Exact + semantic cache (Redis) for repeated questions
  \item Pre-authored FAQ for top 50 Dorchester questions (admin-maintained)
\end{itemize}

\subsubsection{Tier 1 --- Intent Classification ($\leq$ 200ms)}
Use a \textbf{hybrid classifier}, not a generative LLM router:

\begin{table}[h]
\centering
\small
\begin{tabular}{@{}lp{8cm}@{}}
\toprule
\textbf{Signal} & \textbf{Method} \\
\midrule
Keywords & 311, crime, event, meeting, DotNews, street names \\
Patterns & Regex for dates, ``this week'', ``last month'' \\
Light model & Small classifier (Gemini Flash) $\rightarrow$ intent label \\
Confidence & If low $\rightarrow$ \texttt{hybrid\_light} with tight timeouts \\
\bottomrule
\end{tabular}
\end{table}

\textbf{Intent taxonomy (fixed, $\sim$12 labels):}
\begin{verbatim}
events_list | events_detail | 311_stats | 911_stats | safety_trend |
news_recent | policy_doc | neighborhood_fact | city_service_howto |
community_note | chitchat | unknown
\end{verbatim}

\textbf{Critical rule:} Classification must not be a separate generative LLM call with JSON-parse fallback to hybrid (the slowest path).

\subsubsection{Tier 2 --- Data Fetch (parallel, $\leq$ 800ms)}
\begin{table}[h]
\centering
\small
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Intent} & \textbf{Data Source} & \textbf{Technique} \\
\midrule
\texttt{events\_list} & \texttt{events\_materialized} & Zero LLM; SQL + template \\
\texttt{311\_stats} & Aggregated 311 views & Parameterized SQL only \\
\texttt{911\_stats} & Aggregated 911 views & SQL + safety copy rules \\
\texttt{news\_recent} & Vector + BM25 & Top-$k$=8, parallel sources \\
\texttt{policy\_doc} & Policies collection & Higher $k$, rerank top 5 \\
\texttt{hybrid\_light} & SQL slice + vector slice & Parallel execution \\
\bottomrule
\end{tabular}
\end{table}

\textbf{Never} generate SQL with an LLM on the hot path for common intents. Use a \textbf{prepared query library} (20--40 named queries). LLM$\rightarrow$SQL only for novel analytical questions, with 2s timeout and graceful fallback.

\subsubsection{Tier 3 --- Answer Synthesis (one LLM call, $\leq$ 2.5s)}
\begin{itemize}[noitemsep]
  \item Single main model call with question + structured context JSON + citation instructions
  \item Fast capable model (e.g.\ Gemini 2.5 Flash); Pro reserved for admin tools
  \item Streaming starts as soon as first tokens arrive
  \item Hard timeout: 3s $\rightarrow$ partial answer or cached stale response
\end{itemize}

\section{Feature-Specific Design}

\subsection{Chat Authentication}
\textbf{Guest model:}
\begin{itemize}[noitemsep]
  \item \texttt{POST /auth/guest} $\rightarrow$ ephemeral user + Bearer token (tab-scoped)
  \item Rate limit: 30 guests/hour/IP; 60 messages/hour/session
  \item No thread migration on login (fresh registered session)
\end{itemize}

\textbf{Registered model:}
\begin{itemize}[noitemsep]
  \item HttpOnly session cookie + CSRF double-submit
  \item Threads persist across devices; optional password auth
\end{itemize}

\textbf{Conversation state example:}
\begin{lstlisting}
{
  "last_intent": "311_stats",
  "last_neighborhood": "Dorchester",
  "last_sql_result_id": "mv_311_weekly:week12",
  "retrieval_doc_ids": ["news_123", "policy_45"]
}
\end{lstlisting}

\subsection{Events Panel}
\textbf{Design rule:} Events panel is \textbf{100\% decoupled} from the LLM.

\begin{lstlisting}
GET /events?days_ahead=14&limit=20&neighborhood=dorchester
  -> reads events_materialized only
  -> p95 < 100 ms
\end{lstlisting}

Panel prefetches on app load (parallel with \texttt{/auth/me}). Client caches 5 minutes with ETag support.

\subsection{Boston.gov Enrichment (Off Hot Path)}
When synthesis confidence is low:
\begin{enumerate}[noitemsep]
  \item Return initial streamed answer immediately.
  \item Trigger async job to fetch Boston.gov / city page.
  \item Push \texttt{correction} SSE event or ``Updated answer'' toast.
\end{enumerate}

\subsection{Flagging and Feedback}
\begin{itemize}[noitemsep]
  \item \texttt{PUT /interactions/:id/flag} with ownership verification
  \item Flags feed admin queue and optional retraining corpus
  \item Rate-limit flags to prevent abuse
\end{itemize}

\section{Retrieval and Answer Quality}

\subsection{Hybrid Search Pipeline}
\begin{enumerate}[noitemsep]
  \item BM25 top 20 (exact street names, source names)
  \item Vector top 20 (semantic)
  \item Reciprocal Rank Fusion $\rightarrow$ top 8
  \item Cross-encoder rerank (optional, $\leq$ 200ms) for \texttt{policy\_doc} intent
  \item Pass top 5 chunks to synthesis LLM
\end{enumerate}

\subsection{Chunking Strategy}
\begin{table}[h]
\centering
\small
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Content} & \textbf{Chunk Size} & \textbf{Metadata} \\
\midrule
News & 400--600 tokens & \texttt{published\_at}, \texttt{source}, \texttt{url} \\
Policy PDFs & 800 tokens, overlap 100 & \texttt{section}, \texttt{page} \\
Transcripts & Speaker-aware segments & \texttt{meeting\_date} \\
Community notes & Whole note if $<$ 300 tokens & \texttt{expires\_at}, \texttt{category} \\
\bottomrule
\end{tabular}
\end{table}

\subsection{Grounding Contract}
Every synthesis prompt enforces:
\begin{itemize}[noitemsep]
  \item Use only provided \texttt{CONTEXT}; cite sources as [1], [2].
  \item If \texttt{CONTEXT} is insufficient, state what is missing.
  \item Never invent statistics; never expose raw addresses from 911 rows.
\end{itemize}

\subsection{Safety (911 / Crime)}
\begin{itemize}[noitemsep]
  \item Aggregate by neighborhood and time --- no voyeuristic incident narratives.
  \item Suppress counts $<$ 5 in small geographic areas.
  \item Fixed disclaimer on safety answers; human review queue for flagged responses.
\end{itemize}

\section{Summary}

The optimal Dorchester chatbot for \textbf{130,000 residents} is not a bigger LLM pipeline. It is:

\begin{enumerate}[noitemsep]
  \item \textbf{Precomputed civic data} (311, 911, events) served by SQL and templates for common questions.
  \item \textbf{One fast synthesis call} with parallel retrieval, not a chain of routing models.
  \item \textbf{Managed infrastructure} (PostgreSQL, Redis, Qdrant) --- not file-locked SQLite vector stores.
  \item \textbf{Decoupled surfaces} --- events panel and admin never compete with chat for LLM time.
  \item \textbf{Aggressive caching} with clear freshness SLAs and visible degradation.
  \item \textbf{Async ingestion} with incremental upserts and blue-green index swaps.
\end{enumerate}

Built this way, \textbf{p50 $\approx$ 1.5--2.5s} and \textbf{p95 $\leq$ 5s} is achievable for the majority of resident questions, while keeping the system stable, updatable, and operable at community scale.
